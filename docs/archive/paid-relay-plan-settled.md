### 2. ~~認証の具体（フェーズ 1 の設計）~~ → **2026-09-12 に決着（[relay#57](https://github.com/pooza/capsicum-relay/issues/57)）**

#### 2-1. 発行単位: **端末ごとに発行し、購入へ束ねる**

**entitlement の主体は「購入」**（ストアアカウントに属する）。**`entitlement_token` はその下に端末ごとにぶら下がる。**

- ⚠ **購入は複数端末で復元される**（サブスクはストアの購入復元の対象）ので、1 購入に N token
- **端末単位で無効化できる**（token が漏れたときに購入ごと止めずに済む）
- ⚠ **1 購入あたりの端末数に上限を設けない。**対象者 0 人から始まるので、先回りで制限しない（件数は記録して、異常が出てから考える）

#### 2-2. ⚠⚠ 端末の識別子は**既にある**。新しく作らない

```sql
-- lib/relay/database.rb
CREATE TABLE subscriptions (
  …, device_id TEXT, …   -- ⚠ nullable（#15 / capsicum#932）
)
```

`/register` は**既に `device_id` を任意で受け取っている**（`routes/register.rb:16-23`）。capsicum 側も `device_install_id.dart` で発行・保管済み。→ **entitlement_token はこの `device_id` に紐づける。**

#### 2-3. ⚠⚠ `subscriptions` に列を足さない

**別テーブル 2 本**（`entitlements` = 購入単位 / `entitlement_tokens` = 端末単位）にして、**join で引く**。

⚠ **理由は SQLite の組み替えコスト。**`subscriptions` は CHECK / UNIQUE を変えるたびに `rebuild_subscriptions_table!`（rename → 作り直し → コピー → drop）が要る。⚠⚠ **この組み替えは過去に子テーブルの FK を壊している** — `announcement_subscriptions` の FK が `subscriptions_old` を指したまま残り、**自己修復コード（`repair_announcement_subscriptions_fk!`）が今もコードに居座っている**（capsicum#468）。

→ **課金の都合で push の中核テーブルを組み替えない。**

#### 2-4. 判定の経路

```text
/push/{push_token}
  → subscriptions（push_token UNIQUE で 1 行）
  → subscriptions.device_id
  → entitlement_tokens（device_id）
  → entitlements.status
```

⚠ **`device_id` が NULL の行（旧クライアント）は entitlement を引けない。**ゲートは「非プリセット かつ entitlement 無し」で閉じるので、**非プリセットの旧クライアントは止まる**。→ ⚠ **実測で該当は 0 人**（プリセットを 1 つも持たない利用者は 0 人・1-2）。**ただしフェーズ 3 でゲートを実際に閉じる前に測り直すこと。**

#### 2-5. `supporters` テーブルは流用しない

`supporters` は **`UNIQUE(account, server)` ＝ fedi アカウント単位**で、**クライアントの自己申告を記録するだけ**（#596）。⚠ **課金はストアアカウントに紐づく**ので主体が違う。**投げ銭の記録として残し、entitlement とは別物として扱う。**

#### 2-6. 移行

⚠ **フェーズ 1〜2 では誰も拒まない**ので、既存ユーザーへの影響はゼロ。⚠ **唯一の危険点はフェーズ 3 でゲートを実際に閉じる瞬間**で、そこは 2-4 の実測をやり直してから踏む。

⚠ **共有シークレットは残す**（1-1）。認証は二重になる。**置き換えではない。**

### 3. ~~⚠⚠ 「プリセット 1 アカウントで全部無償」の穴をどうするか~~ → **2026-09-12 に決着。a（穴を残す）**

**決定: 穴は塞がない。**

- **非目標「(B) 既存の無料プッシュを課金化 ではない」に一切触れない**（既存ユーザーの通知が止まらない）
- **迂回にはプリセットサーバーへの登録が要る**ので、入口は pooza が握っている
- ⚠ **capsicum の主目的は自前インフラとの連携**なので、**外部ユーザーがプリセットに来ること自体は目的と矛盾しない**
- ⚠ **実装が単純になる。**ゲートの判定は「非プリセット かつ entitlement 無し」だけを見ればよく、**登録時期の記録（b 案）が要らない**

⚠ **これは「迂回されてもよい」ではなく「迂回路がプリセットへの導線になっている」という読み替え。**⚠ **迂回が増えたときに評価をやり直す材料は、プリセットの新規登録数**（既に観測できる）。

#### 2026-09-28 の再評価 —— **決定（a）は変えない。崩れたのは根拠の 1 行だけ**

⚠⚠ **[relay#69](https://github.com/pooza/capsicum-relay/issues/69) により、上の「迂回にはプリセットサーバーへの登録が要る」が成立していないことが分かった。**relay は `/register` が受け取った `server` を検証しておらず、**アカウントを作らずに「プリセットのユーザーです」と申告するだけ**でゲートを抜けられる。

⚠⚠ **ただし pooza の意図は「迂回を塞ぐ」ではない。迂回そのものは意図どおりである**（2026-09-28）。

> 上の例だと、美食丼にアカウントを作ったユーザーは身内だとみなせます。**美食丼は、そもそも私の知り合いしか誘わないことになっている**からです。この様なユーザーは身内だから、たとえ Fedibird で利用したいのが本音だとしても、**capsicum への意見をフィードバックしてくれるでしょう**。（そのフィードバックが「Fedibird の独自要素との相性が悪い」などでしたら却下しますけど）ここまでを踏まえて、**迂回はむしろ意図通りです。**（2026-09-28 pooza）

> いずれにしても、**プリセットサーバーのユーザーは、私個人の活動に興味を持ってくれていると概ね言える**と思います。**この様なユーザーの利益を最大化したいのは変わらない前提です。**（同）

⚠ **「導線」の読み替えは弱まったのではなく、むしろ強い。**本書は迂回の対価を「**うちのサーバーに人が増える**」と評価していたが、実際の対価は「**身内が増える＝ capsicum へのフィードバックが増える**」である。⚠ **プリセットサーバーの入口は技術ではなく人で絞られている**（美食丼は招待制）。

→ **したがって直すべきは根拠の 1 行であって、決定ではない。**

| --- | --- | --- |
| 決定 | a（穴を残す） | **a のまま** |

| ⚠ 壊れていた点 | —— | **relay が申告を検証しておらず、登録しなくても迂回できた**（#69）。**これでは身内化が起きず、読み替えの前提が消える** |

#### 直し方は A 案（VAPID の JWT 検証・2026-09-28 pooza 決定）

⚠ **relay#69 の A 案を採る。**`/push` で **VAPID の JWT を検証**し、プリセットを名乗る push は**プリセット 5 サーバーの公開鍵のいずれかで署名されていること**を要求する。push は fedi サーバー自身が投げるので、`Authorization: vapid t=<jwt>, k=<key>` の署名検証が成立する。

- ⚠ **これは「穴を塞ぐ」ではない。****穴（プリセット 1 アカウントで全部無償）はそのまま残す。**塞ぐのは「**アカウントを作らずにプリセットを名乗れてしまう**」という別の穴
- ⚠ **fail-open は維持する**（決定済み事項 2-C）。検証できないときにプリセットの通知を止めるほうが取り返しがつかない
- ⚠ **未調査: プリセット 5 サーバーの VAPID 公開鍵をどう取得・更新するか**（relay#69 の完了条件）
- ⚠⚠ **C 案（クライアントの fedi アクセストークンを relay が検証）は採らない。**relay が利用者の認証情報を持つことになり、「relay は復号しない / 資格情報を持たない」という設計の柱を壊す

### 3-2. ⚠⚠ ~~`410 Gone` で購読が消えるかは未実測~~ → **2026-09-27 に実測（[relay#60](https://github.com/pooza/capsicum-relay/issues/60)）**

本書 4-2 が「**410 が正しいと書いたが実測していない**」としていた前提。**ソースと実機の両方で確定した。**

#### フォークのソース（⚠ 推測で語らないための一次情報）

| | 購読を消す条件 |
| --- | --- |
| **Mastodon** `Web::PushNotificationWorker#send` | ⚠ **`408` / `429` 以外の 4xx すべて** |
| **Misskey** `PushNotificationService` | ⚠⚠ **`410` だけ**（`if (err.statusCode === 410)`）。**403 / 404 では消さず永久に叩き続ける** |

→ ⚠⚠ **両方に効くのは 410 だけ。**本書は「黙って 200 を返すと永久に叩かれる」と書いていたが、**403 / 404 でも Misskey については同じ**だった。`/push` の拒否は 410 以外にできない。

#### ステージングでの実測（`st2.mstdn.b-shock.org` → st.relay）

⚠ **既存の購読には触らず**、relay が知らない `push_token` を指す購読を 1 件だけ作って踏んだ。nginx のアクセスログに `POST /push/… 410`、**Mastodon 側で購読が destroy された**（既存 2 件は無傷）。

#### 4-2 の「使った実績が無い」は解消した

⚠ `st2.mstdn.b-shock.org → st.relay` の Web Push が**直近 7 日で 4 件**届いている（journald 実測）。

⚠ **ただし `st2.misskey.delmulin.com → st.relay` は 0 件**（購読行はあるが通知が発生していない）。**Misskey 側のライブ確認は未了**でソース読みのみ。⚠ **Misskey は 410 でしか消さない**ので、[relay#62](https://github.com/pooza/capsicum-relay/issues/62) の回にここも踏む。

## FAQ に足す 1 項目

[`capsicum-site/faq/index.md`](https://github.com/pooza/capsicum-site/blob/main/faq/index.md) の「プッシュ通知は誰でも使えますか？」の直後に置く。

```markdown
## 支払いが確認できなくなると通知はどうなりますか？

購読のお支払いが確認できない状態（カードの有効期限切れ・残高不足など）になると、プリセットサーバー以外へのプッシュ通知は止まります。ストアでお支払い方法を更新したあと、capsicum を起動すると通知の登録がやり直され、再び届くようになります。アプリの「設定 → プッシュ通知」で、いまどの状態かを確認できます。
```

⚠⚠ **「起動すると再登録される」を必ず書く。**通知が止まるとき relay は `410 Gone` を返し、**fedi サーバー側の購読が消える**ので、**支払いを直しただけでは戻らない**（relay#63 で受け入れた挙動）。ここが抜けると「直したのに来ない」という問い合わせになる。

⚠ **「常日頃から決済手段を意識してください」という常設の注意は置かない**（2026-10-03 pooza と合意）。買う前に読んでも、支払いが滞る数か月後には参照されない。**事が起きたときにその画面で言う**（capsicum#1123 の登録ステータス画面とローカル通知）を主にして、FAQ は参照先として置く。

## 告知（fedi）

⚠ **告知は fedi で足りる**（site を併用するかは緊急性と深刻度で決める）。⚠ **プリセットサーバーの利用者には関係が無い**ことを最初に書く —— 大多数がそちらなので、書かないと「有償化された」と読まれる。

```text
capsicum に、プリセットサーバー以外でもプッシュ通知を受け取れる月額 ¥200 の
オプションを追加しました。

◇ プリセットサーバー（美食丼・デルムリン丼・キュアスタ！・きゅあすきー・
ダイスキー）をお使いの方は、これまでどおり無償で通知が届きます。購入は不要です。

◇ それ以外のサーバーをお使いの方は、アプリの「設定 → プッシュ通知」から購入すると
プッシュ通知が届くようになります。

#capsicum
```

⚠ **「無償のまま」を先に、「有償の対象」を後に書く。**順序を逆にすると、関係のない大多数が身構える。

⚠⚠ **案内する経路は「設定 → プッシュ通知」。**🔴 **「設定 → サポート」は実在しない** —— 投げ銭の導線は #853 で**設定から外し**、**左ドロワー直下**（「capsicum をサポート」）と**デスクトップのメニューバー**（「capsicum をサポート…」）へ格上げした。⚠ 設定画面に残っているのは「プッシュ通知」で、#1224 で**利用権の節が 2 画面で完全に同じ**になったので、**購入も法定表記もこちらで揃う**（`showLegalNotice: true`）。⚠ しかもこの節は**非プリセットかつ利用権なしのときだけ出る** ＝ 告知の読み手にそのまま当たる。⚠ **プラットフォームで言い方が変わらない**のも利点（ドロワーとメニューバーは端末で違う）。
