## 決定済み事項

### 1. v2.0 は売りを 3 本束ねるメジャーリリース

**v2.0 = [#720](https://github.com/pooza/capsicum/issues/720) + [#597](https://github.com/pooza/capsicum/issues/597) + [#884](https://github.com/pooza/capsicum/issues/884)。**

| Issue | 規模 | 売りとしての位置 |
| --- | --- | --- |
| **#720 デッキ表示** | メジャー | **UI の土台の組み替え。**2.0 を名乗る根拠そのもの。⚠ **外せない** |
| **#597 有償プッシュ通知リレー** | 大更新 | **収益の柱。**プリセット外のユーザーへ初めて有償で価値を出す |
| **#884 画像編集のレイヤ管理** | 大更新 | 投稿体験の目玉 |

⚠ **v2.1 以降は今決めない。**v2.0 の出荷後に、そのときの残件で決める。先に切ると description が陳腐化する（[milestone-transition.md](milestone-transition.md) §5 の「集約枠はリリースが近づいてから」と同じ理由）。**例外は #884 を逃がすと決めた場合**（決定済み事項 3）。

### 2. 1.x と 2.x の境界は「製品判断」であって技術的な線ではない

**1.x は止められない。**#720 / #597 とも設計書すら無く、設計 → Issue 分解 → 実装で長期になる。その間もユーザー報告・Mastodon / Misskey の追従・Sentry の新着は発生し続けるので、「v2.0 まで 1.x 凍結」は成立しない。**1.x と 2.x は並走系列**になる。したがって境界は**バージョンの切り替え時期ではない**。

⚠⚠ **境界の基準を「土台を組み替えるか」という技術構造から導こうとして失敗した**（2026-09-04・当初案の誤り）。その基準だと #597 / #884 は土台を変えないので 1.x になるが、**実際には 2 件とも 2.0 の売りとして最初から想定されていた**。

**メジャーに何を載せるかは製品判断（売りの束ね方）で、pooza が決める。**技術的な規模・構造から機械的に導けるものではない。

| | 行き先 |
| --- | --- |
| **メジャーの売りとして束ねると決めたもの** | **2.x**（＝ pooza の判断） |
| **それ以外すべて** | **1.x**。外部要因（ユーザー報告・上流追従・Sentry）/ 棚卸しの成果 / 単独で出せる大更新 |

⚠ **技術規模が決めるのは別のこと。**「点リリースで単独配置するか」と「メジャーが万一入りきらないとき、どれから逃がすか」の 2 つだけ。**系列（1.x / 2.x）は決めない。**

### 3. v2.0 の容量は通常枠の数倍・逃がし弁は #884

> 2.0 の容量は通常の数倍ぐらいの認識でもあった（2026-09-04 pooza）

**大玉 3 件は過積載ではなく想定内。**CLAUDE.md の「1 マイルストーンに大更新 0〜1 件 + 小粒・中粒 5〜12 件」は**点リリース（1.x）の目安**で、この枠には当てない。

**実データでも裏付けられる**（2026-09-04 実測）:

| | 件数 |
| --- | --- |
| **v1.0**（最大の枠） | **Issue 46 件**（+ PR 9 件） |
| v1.25 / v1.24 / v1.26 | 40 / 32 / 26 件 |
| **v1.50〜v1.62 の平均** | **13 件**（最大 19・最小 4） |

→ **v1.0 は直近の通常枠の約 3.5 倍**。「メジャー級の枠は通常の数倍」という認識は実績と合っている。

⚠ **ただし「100 近く」ではない。**最大は v1.0 の 46 件（PR を足しても 55 件）で、100 に届いた枠は存在しない。**目安として数字を引くときはこの表を見ること**（記憶で「100 件規模」と書くと、v2.0 の規模見積もりが倍ずれる）。

⚠ **「大更新が 3 件あるから分割しましょう」と提案しないこと。**規約違反ではなく、メジャー枠として正常な状態。

⚠ **ただし規約の目的（設計検討・実装・動作確認がいずれも中途半端になるのを防ぐ）は守る。**容量が大きいのは**リリースの単位**の話で、作業を並走させてよい意味ではない。**設計書は 1 本ずつ・実装も逐次。**

**逃がし弁は [#884](https://github.com/pooza/capsicum/issues/884)**（2026-09-04 pooza「884 は 2.0 が過積載なら、2.x としてもよいかなとおもってました」）。⚠ **容量的には 3 本入る想定なので通常は動かさない。**設計書が出て規模が読めた段階で、本当に入りきらないと分かったときだけ v2.1 へ送る。

⚠ **逃がす順序を迷わないために先に決めてある。**#720 は 2.0 を名乗る根拠そのもので外せない。#597 は収益の柱で relay 側の実装も伴うため分離コストが高い。**#884 は投稿フォーム内で閉じるので、単独で切り出しても他に波及しない。**

### 3. メンテナンスモードは終了する

分類 B の 13 件は**全件が内部由来**（ユーザー要望由来はゼロ・2026-09-04 に全件の本文を確認）。これを 1.x の通常枠で順次消化すると決めたので、**「外部要因の発生ベースで回す」運用（2026-08-17〜）はここで終わる。**

- ⚠ **v1.63 の「内部由来を入れてよい枠ではない」という制約は、この枠に限った歴史的経緯として残す。**v1.65 以降には掛からない
- **未割り当てだった [#1034](https://github.com/pooza/capsicum/issues/1034) / [#1035](https://github.com/pooza/capsicum/issues/1035) / [#1038](https://github.com/pooza/capsicum/issues/1038) は 2026-09-04 に割り当てた**（下記）。reactive 運用の下で「内部由来だから」と意図的に外していた 3 件で、**モードが終わって外す理由が消えた**ため

### 4. 棚卸しの続き 4 件は 1.x の枠に入れる

調査の成果は「種」であり、種の行き先（分類 B）が 1.x なら調査も 1.x が自然。

⚠ **[#1046](https://github.com/pooza/capsicum/issues/1046) と [#1077](https://github.com/pooza/capsicum/issues/1077) は同じ枠に入れる。**母数が重なるので別々に回すと同じコードを 2 回読むことになる。ただし**数え方（API 基準 / WebUI 基準）は 2 通り維持する** — 片方でしか出ない項目が実際にあったため。

### 5. 枠の主題

⚠ **確定度が枠によって違う。**直近 2 枠は含有 Issue まで確定、それ以降は**主題だけ確定**で中身は近づいてから精査する。

⚠ **v2.0 の「3 件」を薄いと読まない。**大玉 3 件で、容量の目安が違う（決定済み事項 3）。

### 6. 「閲覧のみ」の族は 1 つ目で 5 つ分の型を決める

[#1050](https://github.com/pooza/capsicum/issues/1050) クリップ / [#1051](https://github.com/pooza/capsicum/issues/1051) チャンネル / [#1052](https://github.com/pooza/capsicum/issues/1052) アンテナ / [#1053](https://github.com/pooza/capsicum/issues/1053) ギャラリー / [#1073](https://github.com/pooza/capsicum/issues/1073) Pages の 5 件は**同じ設計問題を共有する**（閲覧だけ実装済みで、作成・編集の導線が無い）。

- **v1.65 で #1050 → #1051 → #1052 の順に触る。**#1050 で 5 件分の型（一覧 → 作成 → 編集の画面構成・保存の扱い・失敗時の戻し方）を決める
- **#1053 / #1073 は v1.66 へ送る。**型が決まってからの方が安い。⚠ #1053 は独立機能で作成まで入れると 1 枠ぶんあるため大更新扱い。⚠ #1073 は他の 4 件と違い**自分のページ一覧すら無い**ので、`i/pages` だけ先に足す分割もありうる
- ⚠ **[#1074](https://github.com/pooza/capsicum/issues/1074)（Play の作成・編集）は束に混ぜない。**AiScript エディタを載せる話になり性質が違う

### 7. 「決着そのものが成果」の Issue を混ぜて置く

[#1049](https://github.com/pooza/capsicum/issues/1049) トレンド / [#1074](https://github.com/pooza/capsicum/issues/1074) Play の作成・編集 / [#1079](https://github.com/pooza/capsicum/issues/1079) preferences の 3 設定は、**「やる / やらないの決着」で完了してよい**型。⚠ **3 件とも分類 C（拾わない）行きがありうる。**

実装が要ると決まった時点で別 Issue に割る。**決着だけなら軽いので、大更新のある枠にも混ぜられる。**
