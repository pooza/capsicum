### 2. 1.x と 2.x の境界は「製品判断」であって技術的な線ではない

**1.x は止められない。**#720 / #597 とも設計書すら無く、設計 → Issue 分解 → 実装で長期になる。その間もユーザー報告・Mastodon / Misskey の追従・Sentry の新着は発生し続けるので、「v2.0 まで 1.x 凍結」は成立しない。**1.x と 2.x は並走系列**になる。したがって境界は**バージョンの切り替え時期ではない**。

⚠⚠ **境界の基準を「土台を組み替えるか」という技術構造から導こうとして失敗した**（2026-09-04・当初案の誤り）。その基準だと #597 / #884 は土台を変えないので 1.x になるが、**実際には 2 件とも 2.0 の売りとして最初から想定されていた**。

**メジャーに何を載せるかは製品判断（売りの束ね方）で、pooza が決める。**技術的な規模・構造から機械的に導けるものではない。

| | 行き先 |
| --- | --- |
| **メジャーの売りとして束ねると決めたもの** | **2.x**（＝ pooza の判断） |
| **それ以外すべて** | **1.x**。外部要因（ユーザー報告・上流追従・Sentry）/ 棚卸しの成果 / 単独で出せる大更新 |

⚠ **技術規模が決めるのは別のこと。**「点リリースで単独配置するか」と「メジャーが万一入りきらないとき、どれから逃がすか」の 2 つだけ。**系列（1.x / 2.x）は決めない。**

### 3. v2.0 の容量は通常枠の数倍・逃がし弁は #884

> 2.0 の容量は通常の数倍ぐらいの認識でもあった（2026-09-04 pooza）

**大玉 3 件は過積載ではなく想定内。**CLAUDE.md の「1 マイルストーンに大更新 0〜1 件 + 小粒・中粒 5〜12 件」は**点リリース（1.x）の目安**で、この枠には当てない。

**実データでも裏付けられる**（2026-09-04 実測）:

| | 件数 |
| --- | --- |
| **v1.0**（最大の枠） | **Issue 46 件**（+ PR 9 件） |
| v1.25 / v1.24 / v1.26 | 40 / 32 / 26 件 |
| **v1.50〜v1.62 の平均** | **13 件**（最大 19・最小 4） |

→ **v1.0 は直近の通常枠の約 3.5 倍**。「メジャー級の枠は通常の数倍」という認識は実績と合っている。

⚠ **ただし「100 近く」ではない。**最大は v1.0 の 46 件（PR を足しても 55 件）で、100 に届いた枠は存在しない。**目安として数字を引くときはこの表を見ること**（記憶で「100 件規模」と書くと、v2.0 の規模見積もりが倍ずれる）。

⚠ **「大更新が 3 件あるから分割しましょう」と提案しないこと。**規約違反ではなく、メジャー枠として正常な状態。

⚠ **ただし規約の目的（設計検討・実装・動作確認がいずれも中途半端になるのを防ぐ）は守る。**容量が大きいのは**リリースの単位**の話で、作業を並走させてよい意味ではない。**設計書は 1 本ずつ・実装も逐次。**

#### 過積載の懸念の実体と、逃がす順序

> 大玉 3 と B 11 がさすがに過積載になりうるかなと思っていました。やりきれるなら良しです（2026-09-04 pooza）

**逃がす順序**（先に決めておき、そのとき迷わない）:

| 順 | 逃がす対象 | 理由 |

#### 1.x へ引き上げた 2 件（2026-09-04 pooza 判断）

判断軸は **読む側に継続的な実害があるか**。

| Issue | 実害 |
| --- | --- |
| [#1055](https://github.com/pooza/capsicum/issues/1055) 引っ越し済みアカウントの表示 | **フォローしているのに投稿が来ない人がそのまま残り、引っ越し先へ辿る導線が無い。**Account モデルに `moved` / `movedTo` を足すだけなので読む側は小粒 |
| [#1054](https://github.com/pooza/capsicum/issues/1054) 編集済み投稿に印を出す | ⚠ **capsicum 自身が「無音の編集」を作っている**（下記） |

⚠⚠ **#1054 は「自前サーバーでは編集できないから要らない」が成り立たない。**2026-09-04 にフォークを実測した結果:

- サーバー側は**禁止ではなく「理由を申告させて妥当なものだけ通す」設計**。WebUI のメニューは落としてある（`status_action_bar/index.jsx` のコメントアウト 1 行）が、**`statuses_controller.rb` の diff は空で `PUT /api/v1/statuses/:id` は生きている**。nginx 前段が `X-Mulukhiya-Purpose` の申告を見て振り分ける（mulukhiya#4474）
- **capsicum の ALT 編集（[#121](https://github.com/pooza/capsicum/issues/121)・v1.60 出荷済み）は `media_update` を申告して通っている側**。ALT は投稿編集 API を通す以外に書き換える手段が無いため
- **その結果 `edited_at` が立つ**（`update_status_service.rb:59` → `media_attachment.rb:250-252` の `significantly_changed?` が `description_previously_changed?` を含む → `create_edit!`）
- → **サーバー側は理由の申告まで要求しているのに、読む側には何も出ていない。**経路は正当なのに結果が無音、という状態

**方針「投稿者の責任として、投稿を無音で編集されうる機能は Mastodon には存在するべきではない」**（2026-09-04 pooza）と真正面から噛み合う。詳細は [#1054 のコメント](https://github.com/pooza/capsicum/issues/1054#issuecomment-5530367323)。
