| Issue | 規模 | 売りとしての位置 |

⚠ **v2.1 以降は今決めない。**v2.0 の出荷後に、そのときの残件で決める。先に切ると description が陳腐化する（[milestone-transition.md](milestone-transition.md) §5 の「集約枠はリリースが近づいてから」と同じ理由）。**例外は #884 を逃がすと決めた場合**（決定済み事項 3）。

### 2. 1.x と 2.x の境界は「製品判断」であって技術的な線ではない

**1.x は止められない。**#720 / #597 とも設計書すら無く、設計 → Issue 分解 → 実装で長期になる。その間もユーザー報告・Mastodon / Misskey の追従・Sentry の新着は発生し続けるので、「v2.0 まで 1.x 凍結」は成立しない。**1.x と 2.x は並走系列**になる。したがって境界は**バージョンの切り替え時期ではない**。

⚠⚠ **境界の基準を「土台を組み替えるか」という技術構造から導こうとして失敗した**（2026-09-04・当初案の誤り）。その基準だと #597 / #884 は土台を変えないので 1.x になるが、**実際には 2 件とも 2.0 の売りとして最初から想定されていた**。

**メジャーに何を載せるかは製品判断（売りの束ね方）で、pooza が決める。**技術的な規模・構造から機械的に導けるものではない。

| | 行き先 |
| --- | --- |
| **メジャーの売りとして束ねると決めたもの** | **2.x**（＝ pooza の判断） |
| **それ以外すべて** | **1.x**。外部要因（ユーザー報告・上流追従・Sentry）/ 棚卸しの成果 / 単独で出せる大更新 |

⚠ **技術規模が決めるのは別のこと。**「点リリースで単独配置するか」と「メジャーが万一入りきらないとき、どれから逃がすか」の 2 つだけ。**系列（1.x / 2.x）は決めない。**

### 3. v2.0 の容量は通常枠の数倍・逃がし弁は #884

> 2.0 の容量は通常の数倍ぐらいの認識でもあった（2026-09-04 pooza）

**大玉 3 件は過積載ではなく想定内。**CLAUDE.md の「1 マイルストーンに大更新 0〜1 件 + 小粒・中粒 5〜12 件」は**メジャーアップグレード（x.0）以外の枠の目安**で、この枠には当てない。

⚠⚠ **「以外」には x.1 以降も含む**（2026-09-23 pooza）。**特例が当たるのはメジャーアップグレードの枠だけ**で、**2.x という系列に当たるのではない**。⚠ v2.1 をこの読み違いで過積載にした実例がある（下の「2026-09-23」節）。⚠ **次に当たるのは 3.0 だが、起こすネタが無いので当分は発生しない見込み。**

**実データでも裏付けられる**（2026-09-04 実測）:

| | 件数 |
| --- | --- |
| **v1.0**（最大の枠） | **Issue 46 件**（+ PR 9 件） |
| v1.25 / v1.24 / v1.26 | 40 / 32 / 26 件 |
| **v1.50〜v1.62 の平均** | **13 件**（最大 19・最小 4） |

→ **v1.0 は直近の通常枠の約 3.5 倍**。「メジャー級の枠は通常の数倍」という認識は実績と合っている。

⚠ **ただし「100 近く」ではない。**最大は v1.0 の 46 件（PR を足しても 55 件）で、100 に届いた枠は存在しない。**目安として数字を引くときはこの表を見ること**（記憶で「100 件規模」と書くと、v2.0 の規模見積もりが倍ずれる）。

⚠ **「大更新が 3 件あるから分割しましょう」と提案しないこと。**規約違反ではなく、メジャー枠として正常な状態。

⚠ **ただし規約の目的（設計検討・実装・動作確認がいずれも中途半端になるのを防ぐ）は守る。**容量が大きいのは**リリースの単位**の話で、作業を並走させてよい意味ではない。**設計書は 1 本ずつ・実装も逐次。**

#### 過積載の懸念の実体と、逃がす順序

> 大玉 3 と B 11 がさすがに過積載になりうるかなと思っていました。やりきれるなら良しです（2026-09-04 pooza）

**懸念の対象は #884 単独ではなく、v2.0 全体の 18 件**（大玉 3 + 分類 B 11 + 棚卸しの続き 4）。

⚠ **判断材料は「大玉 3 件が何 Issue に割れるか」で、設計書が出るまで分からない。**#720 / #597 は分解前提の規模なので、**追跡単位は 18 件だが実作業の単位はもっと増える**。実績の最大が v1.0 の 46 件（決定済み事項 3 の表）なので、**大玉の分解後に総数がそこを超えそうなら分割する**、が使える閾値。

**逃がす順序**（先に決めておき、そのとき迷わない）:

| 順 | 逃がす対象 | 理由 |
| --- | --- | --- |
| 1 | **「閲覧のみ」の族の後半**（#1053 ギャラリー / #1073 Pages） | ⚠ **1 つ目で型を決める**設計なので、**型さえ決まれば残りは後回しにできる**（決定済み事項 7）。分割の切れ目として最も自然 |
| 2 | **決着型 3 件**（#1049 / #1074 / #1079） | 「やる / やらないの決着」で完了してよい型なので、**決着だけ 2.0 で付けて実装を 2.1 へ**という半分だけの逃がし方もできる |
| 3 | **[#884](https://github.com/pooza/capsicum/issues/884)** | 投稿フォーム内で閉じるので単独で切り出しても波及しない。⚠ **ただし売りの 1 本なので、逃がすと 2.0 の訴求が 2 本に減る** |

⚠ **#720 と #597 は逃がさない。**#720 は 2.0 を名乗る根拠そのもの。#597 は収益の柱で、relay 側の実装も伴うため分離コストが高い。

⚠ **判断のタイミングは「#720 / #597 の設計書が出た直後」。**それより前に分割すると、何を逃がせば足りるのかが分からないまま切ることになる。

⚠⚠ **以下の 7 節（2026-09-12 〜 2026-10-02）は、v2.0 / v2.1 の枠を配り直した記録。**どちらも出荷済みなので、**当時の件数・枠割りの表・経過は [archive/roadmap-settled.md](archive/roadmap-settled.md) へ移した**（2026-10-11）。ここには**同じ見出しと、いまも効く基準だけ**を残す。⚠ **いまの枠は GitHub Milestones が正本。**

#### 2026-09-19: 順序 1 の残り 3 件も逃がし、**残す側の基準**が決まった
