## 決定済み事項

### 1. 2.x は #720（デッキ UI）のためだけの系列にする

**v2.0 = [#720](https://github.com/pooza/capsicum/issues/720) 単独。**

大玉 3 件のうち、**UI の土台を組み替えるのは #720 だけ**だった。#720 は「ログインアカウント単位のタブ / ドロワー構成」という現在の土台と別レイヤーの設計変更で、Issue 本文でもメジャー級と明記されている。

残る 2 件は 1.x で出した前例がそれぞれある:

| Issue | 規模 | 1.x で出せる根拠 |
| --- | --- | --- |
| [#597](https://github.com/pooza/capsicum/issues/597) 外部ユーザー向け有償リレー | 大更新 | 投げ銭サブスク（[#428](https://github.com/pooza/capsicum/issues/428)）を **v1.27 で単独配置して出荷済み**。課金 SKU の追加は土台を変えない |
| [#884](https://github.com/pooza/capsicum/issues/884) 画像編集のレイヤ管理 | 大更新 | 前段のスタンプ（[#883](https://github.com/pooza/capsicum/issues/883)）を **v1.57 で出荷済み**。投稿フォーム内で閉じる |

→ **#597 / #884 は 1.x の単独大更新枠**に降ろす。

⚠ **v2.1 以降は今決めない。**v2.0 の出荷後に、そのときの残件で決める。先に切ると description が陳腐化する（[milestone-transition.md](milestone-transition.md) §5 の「集約枠はリリースが近づいてから」と同じ理由）。

### 2. 1.x と 2.x の境界は「時期」ではなく「土台を組み替えるか」

**1.x は止められない。**#720 は設計書すら無く、設計 → Issue 分解 → 実装で長期になる。その間もユーザー報告・Mastodon / Misskey の追従・Sentry の新着は発生し続けるので、「v2.0 まで 1.x 凍結」は成立しない。**1.x と 2.x は並走系列**になる。

したがって境界はバージョンの切り替え時期ではなく、**行き先の基準**として定義する。

| | 行き先 |
| --- | --- |
| **既存の土台の上に載るもの** | **1.x**。外部要因（ユーザー報告・上流追従・Sentry）/ 棚卸しの成果 / 大更新でも土台を変えないもの |
| **UI の土台そのものを組み替えるもの** | **2.x** |

⚠ **「規模が大きいから 2.x」ではない。**#597 も #884 も大更新だが 1.x に置く。**規模と系列は独立の軸**として扱う（規模は「独立枠に単独配置するか」を決め、系列は「土台を変えるか」で決まる）。

### 3. メンテナンスモードは終了する

分類 B の 13 件は**全件が内部由来**（ユーザー要望由来はゼロ・2026-09-04 に全件の本文を確認）。これを 1.x の通常枠で順次消化すると決めたので、**「外部要因の発生ベースで回す」運用（2026-08-17〜）はここで終わる。**

- ⚠ **v1.63 の「内部由来を入れてよい枠ではない」という制約は、この枠に限った歴史的経緯として残す。**v1.65 以降には掛からない
- **未割り当てだった [#1034](https://github.com/pooza/capsicum/issues/1034) / [#1035](https://github.com/pooza/capsicum/issues/1035) / [#1038](https://github.com/pooza/capsicum/issues/1038) は 2026-09-04 に割り当てた**（下記）。reactive 運用の下で「内部由来だから」と意図的に外していた 3 件で、**モードが終わって外す理由が消えた**ため

### 4. 棚卸しの続き 4 件は 1.x の枠に入れる

調査の成果は「種」であり、種の行き先（分類 B）が 1.x なら調査も 1.x が自然。

⚠ **[#1046](https://github.com/pooza/capsicum/issues/1046) と [#1077](https://github.com/pooza/capsicum/issues/1077) は同じ枠に入れる。**母数が重なるので別々に回すと同じコードを 2 回読むことになる。ただし**数え方（API 基準 / WebUI 基準）は 2 通り維持する** — 片方でしか出ない項目が実際にあったため。

### 5. 枠の主題

⚠ **確定度が枠によって違う。**直近 2 枠は含有 Issue まで確定、それ以降は**主題だけ確定**で中身は近づいてから精査する。

| 枠 | 主題 | 大更新 | 確定度 |
| --- | --- | --- | --- |
| **v1.63** | 棚卸し 3 本の成果を消化（稼働中） | 0 | 確定・稼働中 |
| **v1.64** | レビュー・Codex 由来の送り分 + #1037 実機検証 | 0 | 確定 |
| **v1.65** | **「閲覧のみ」の型を決める** + 小粒の片付け | 0 | 確定 |

| **v1.69** | **投稿フォームの画像編集レイヤ管理** | 1（#884） | 主題のみ |

⚠ **薄い枠があるのは規約どおり。**大更新は単独配置なので、v1.67 以降は含有件数が少なく見える。**外部要因（ユーザー報告・上流追従・Sentry 起点）は各枠に随時入る**ので、実際にはそこで埋まる。

⚠ **[#597](https://github.com/pooza/capsicum/issues/597) には枠を作らない。**着手律速が「収益判断」と「relay 側の同名枠」で、どちらも判断が出ていない。**枠を先に作ると空枠になる**（[milestone-transition.md](milestone-transition.md) §3-2 の「0 件の枠は『やらない』と区別が付かない」と同じ形）。→ 未決事項 1。⚠ **マイルストーン未設定でも見失わないよう、この文書の未決事項に台帳として残す。**

### 6. 「閲覧のみ」の族は 1 つ目で 5 つ分の型を決める

[#1050](https://github.com/pooza/capsicum/issues/1050) クリップ / [#1051](https://github.com/pooza/capsicum/issues/1051) チャンネル / [#1052](https://github.com/pooza/capsicum/issues/1052) アンテナ / [#1053](https://github.com/pooza/capsicum/issues/1053) ギャラリー / [#1073](https://github.com/pooza/capsicum/issues/1073) Pages の 5 件は**同じ設計問題を共有する**（閲覧だけ実装済みで、作成・編集の導線が無い）。

- **v1.65 で #1050 → #1051 → #1052 の順に触る。**#1050 で 5 件分の型（一覧 → 作成 → 編集の画面構成・保存の扱い・失敗時の戻し方）を決める
- **#1053 / #1073 は v1.66 へ送る。**型が決まってからの方が安い。⚠ #1053 は独立機能で作成まで入れると 1 枠ぶんあるため大更新扱い。⚠ #1073 は他の 4 件と違い**自分のページ一覧すら無い**ので、`i/pages` だけ先に足す分割もありうる
- ⚠ **[#1074](https://github.com/pooza/capsicum/issues/1074)（Play の作成・編集）は束に混ぜない。**AiScript エディタを載せる話になり性質が違う

### 7. 「決着そのものが成果」の Issue を混ぜて置く

[#1049](https://github.com/pooza/capsicum/issues/1049) トレンド / [#1074](https://github.com/pooza/capsicum/issues/1074) Play の作成・編集 / [#1079](https://github.com/pooza/capsicum/issues/1079) preferences の 3 設定は、**「やる / やらないの決着」で完了してよい**型。⚠ **3 件とも分類 C（拾わない）行きがありうる。**
