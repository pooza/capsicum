### 4. カラムキーの形（2026-09-12 決定・[#1087](https://github.com/pooza/capsicum/issues/1087) / [#1088](https://github.com/pooza/capsicum/issues/1088) / [#1091](https://github.com/pooza/capsicum/issues/1091) の共通前提）

1-3 で「カラムの同一性は `(AccountKey, TabType)` で表せる」と書いたが、**実装に落とすと 1 つ罠がある。**

#### 4-1. ⚠⚠ `TabType.toKey()` は永続化キーに使えない（`==` と一致しない）

```dart
// tab_type.dart
class ListTab extends TabType {
  @override
  String toKey() => name != null ? 'list:$id:$name' : 'list:$id';   // ⚠ 表示名が入る

  @override
  bool operator ==(Object other) => other is ListTab && id == other.id;  // ⚠ id だけ
  @override
  int get hashCode => id.hashCode;
}
```

**`toKey()` は表示名を含むのに、`==` / `hashCode` は id しか見ていない。**`ChannelTab` も同型。

→ ⚠⚠ **サーバー側でリスト名を変えると、同じカラムなのにキーだけ別物になる。**カラム ID・キャッシュのスロット名・永続化キーに `toKey()` の文字列をそのまま使うと、**リネームした瞬間にカラムの並び順・設定・キャッシュが「別のカラムのもの」になって消える。**

⚠ **今これが表面化していないのは、既存の永続化が必ず `TabType.fromKey()` で値に戻してから `==` で比較しているから**（`preferences_provider.dart:484-493` のタブ表示設定）。**文字列そのものを同一性として使っている箇所が現状 1 つも無い。**デッキはそれを始める最初の機能になる。

#### 4-2. 決定

| 用途 | 何を使うか |
| --- | --- |
| **provider の family キー** | **値のまま**（`(AccountKey, TabType)` の record）。⚠ `TabType.==` は id ベースなので**これが正しい** |
| **永続化・キャッシュのスロット名・カラム ID** | ⚠ **正規化した文字列**（`list:<id>` / `channel:<id>` — **表示名を落とす**）。`TabType` に `toIdentityKey()` を足し、**`toKey()` は既存の用途のまま触らない**（後方互換） |
| **カラムのラベル** | 実行時に解決する。⚠ **キーに混ぜない** |

#### 4-3. ⚠ 既に同じ形の文字列がある — `timelineContextKey`

```dart
// timeline_provider.dart:50
String? timelineContextKey(AccountKey? accountKey, String kind) =>
    accountKey == null ? null : '${accountKey.toStorageKey()}|$kind';
```

**`<アカウント>|<種別>` は、まさにカラムキーの形をしている**（#758 で TL の文脈照合のために入ったもの）。⚠ **`kind` の語彙だけが `TabType.toKey()` と揃っていない**（`tl:home` 対 `timeline:home`、`tag:` 対 `hashtag:`）。**カラムキーはこの関数の `kind` に `toIdentityKey()` を渡す形に寄せる**と、family キー・キャッシュのスロット・#1086 の streaming キーが 1 本の式に揃う。

⚠ **寄せると起動キャッシュのキーが 1 回変わる**（`tl:home` → `timeline:home`）。**実害は「初回だけ先出しが効かない」**だけ（#890 のキャッシュは load 時にキー不一致なら捨てる）。

### 5. カラムの生死と購読の生死を分ける（2026-09-12 決定・[#1087](https://github.com/pooza/capsicum/issues/1087)）

未決事項 2-B（**可視カラムのみ live・ただし状態は保持**）を実装に落とすと、**「provider を生かしたまま、購読だけ切る」**が要る。現状はこの 2 つが分かれていない。

#### 5-1. ⚠ 購読の開始は build() の副作用になっている

```dart
// timeline_provider.dart:816-818（build の末尾）
if (adapter is StreamSupport && ref.read(streamingEnabledProvider)) {
  _startStreaming(adapter as StreamSupport, type);
}
```

外から止められるのは `streamingEnabledProvider`（**全 ON / 全 OFF の 1 個だけ**）。⚠ **カラム単位の live / not-live という概念が無い。**

#### 5-2. ⚠⚠ 可視性を `ref.watch` で見てはいけない（#904 の再発）

同じ罠を 1 度踏んでおり、**理由がコードのコメントに残っている**:

> 初期判定は read で行う。watch すると、トグル切替が build() 全体（REST 再フェッチ・スクロール位置リセット・`_pendingPosts.clear` 等）を誘発し、可視のスクロールジャンプを起こす (#904)。切替の張り/解除は build() 側の listen。
> — `timeline_provider.dart:811-815`

→ ⚠⚠ **カラムの可視性を `build()` で watch すると、横スクロールのたびに全カラムが REST から取り直され、スクロール位置が飛ぶ。**

**決定: 可視性は `streamingEnabledProvider` と同じ経路に乗せる**（`timeline_provider.dart:674-689` の `ref.listen`）。**張り / 解除だけを listen で行い、build は 1 度も再実行しない。**

```dart
// build() 側（既存の listen の隣に置く）
ref.listen(columnLiveProvider(key), (_, live) {
  live ? _startStreaming(streamAdapter, type) : _stopStreaming(streamAdapter);
});
```

⚠ **猶予（2-B の「画面外に出た瞬間に切らない」）も `columnLiveProvider` の側に置く。**notifier に猶予を持たせると、**同じ遅延が 2 か所（可視判定とカラム）に散る**。

#### 5-3. `autoDispose` は変えない（#1087 の注意書きどおり）

**カラムを生かす責務はデッキコンテナ側に置く** — 列に存在するカラムのウィジェットが watch を保つ限り、`autoDispose` は発火しない。⚠ **横スクロールのコンテナは既定で画面外の子を捨てる**ので、**カラムは明示的に生かす**（#1092 の要件）。

→ **「列から削除する = provider も破棄される」**が自然な対応になり、破棄の条件を別に発明しなくて済む。

### 6. カラム列の編集は「タブ管理」の一般化（2026-09-12 決定・[#1093](https://github.com/pooza/capsicum/issues/1093)）

#### 6-1. 先例がそのままある

| | 現行（タブ） | デッキ（カラム） |
| --- | --- | --- |
| モデル | `TabConfigEntry(tab, visible)` の **順序つきリスト** | `(AccountKey, TabType)` の順序つきリスト |
| 永続化 | `List<String>`（`preferences_provider.dart:484-493`。非表示は `!` 接頭辞） | 同型（キーは 4-2 の `toIdentityKey()`） |
| 編集 UI | `tab_management_sheet.dart` の **`ReorderableListView`**（並べ替え + 表示/非表示） | 同型（+ 追加 / 削除） |

⚠ **新しい UI パターンを持ち込まない。**「並べ替えできるリスト」は既にこのアプリの idiom。

#### 6-2. ⚠⚠ 決定的な差: カラムは**重複できる**

**タブは `TabType` の集合**で、`==` が id ベースなので同じタブを 2 枚持てない。**カラム列は同じ `(AccountKey, TabType)` を 2 本置けてよい**（参考実装もそう）。

→ **「列の要素」と「provider の同一性」を分ける**:

| | 何で識別するか |
| --- | --- |
| **列の要素（並べ替え・削除の対象・Widget の key）** | ⚠ **列内の安定 ID**（追加時に採番）。⚠ **index を使わない**（並べ替えで意味が変わる） |
| **provider の family キー（中身）** | `(AccountKey, TabType)`。⚠ **重複カラムは同じインスタンスを共有する** — 購読も 1 本で済み、メモリも 1 本 |

#### 6-3. ⚠⚠ 削除時に `disconnect` を明示的に呼んではいけない

重複カラムが provider を共有する以上、**「1 本消したら購読も落とす」は間違い**（もう 1 本が無音で止まる。B-1 と同じ壊れ方）。

**正しくは何もしない。**列から消える → watch が減る → **最後の 1 本が消えたときだけ `autoDispose` が発火**し、既存の `ref.onDispose`（`timeline_provider.dart:666-672`）が `disposeStream(key)` を呼ぶ。⚠ **参照カウントを自前で持たない。**

⚠ **#1093 の本文にあった「削除時にそのカラムの購読を確実に落とす（#1089 / #1090 の個別 `disconnect` を使う）」は、この決定で誤りになったので訂正した。**

### 7. デッキ時のナビゲーションと AppBar（2026-09-12 決定・[#1094](https://github.com/pooza/capsicum/issues/1094)）

#### 7-1. 常駐ドロワーはデッキ時だけ出さない（採用）

#1094 が挙げていた 2 案のうち、**「常駐ドロワーをデッキ時だけオーバーレイへ戻す」**を採る。判定は `home_screen.dart:574` の 1 行（`width >= 900`）にデッキ判定を足すだけで閉じる。

⚠ **もう一方の「カラム選択を上下のストリップへ移す」は今はやらない。**1 カラムまで狭まったときの行き来は **#1092 の snap ページャで足りる可能性がある**ので、**実機で測ってから足す**（先回りで UI を増やさない）。

#### 7-2. ⚠⚠ AppBar は「アカウント 1 つ・タブ 1 本」を前提に組んである

```dart
// home_screen.dart:613-692
title: …UserAvatar(account.user) + 表示名 + サーバーバッジ…        // ⚠ 現在のアカウント
actions: [
  if (ref.watch(selectedTabProvider) case TimelineTab(:final type) …)
    const _StreamStatusIndicator(),                                // ⚠ 選択中タブの接続状態
```

⚠⚠ **接続インジケータをデッキで画面共通の AppBar に 1 個だけ置くと、[#793](https://github.com/pooza/capsicum/issues/793) の再発になる。**#793 はまさに「**表示中の内容と無関係な裏のホーム購読状態を出していた**」を直した回で、コメントに経緯が残っている（`home_screen.dart:681-687`）。デッキでは購読が N 本あるので、**1 個のインジケータはどれの状態でもない**。

**決定: 接続インジケータはカラムのヘッダーへ降ろす。**⚠ **未決事項 2-C（カラムごとにソケットを分ける）と噛み合っている** — カラムごとに独立した接続状態が取れるので、**カラム単位のインジケータが素直に作れる**。

⚠ **アカウント表示も同じ。**フェーズ 2 でカラムごとにアカウントが変わると、AppBar のアバターは何も指さなくなる。**カラムヘッダーにアカウントを出す**（フェーズ 1 の時点では全カラム同じアカウントなので実害は無いが、**ヘッダーの置き場だけ先に作っておく**）。

#### 7-3. タブ UI の AppBar の 4 項目をデッキでどうするか（2026-09-26 pooza 決定・[#1173](https://github.com/pooza/capsicum/issues/1173)）

| 項目 | デッキ |
| --- | --- |
| ライブ更新インジケータ | **置かない**（7-2 のとおりカラムの見出しにある） |
| 実況トグル | **置く**。フィルタ自体は既にカラムに効いているので入口だけ。タブ UI の `_LivecureFilterButton` を共有できる形に切り出す |
| 検索 | **置く**。**フォーカス中のカラム**（決定済み事項 10）のアカウントで、**検索画面をカラムとして**フォーカス中のカラムの右隣に開く（`DeckOnlyTab` に種別を足す・#1150 と同じ作業）。⚠ 全画面で開く案は採らない（結果から開いた先がデッキの外になる）。見出しに置く案も採らない（見出しは投稿ボタンで埋まった） |
| 通知（ベル） | **置く**。押すと「**すべての通知**」を**カラムとして**開く（既にあればそこへ送ってフォーカス）。アカウントが 1 つならそのアカウントの通知カラム。「すべての通知」はカラム編集の候補にも足す。未読バッジはタブ UI にも無いので扱わない |

⚠⚠ **「すべての通知」画面は、通知を押すと現在のアカウントを切り替えてから開く**（`unified_notification_screen.dart` の `switchAccount`）。デッキでは現在のアカウントが変わるとカラムのコンテナの割り当てが組み替わる（決定済み事項 8）ので、**そのままデッキに持ち込むと通知 1 つで裏側が組み変わる。**デッキの中では**切り替えずに、その通知のアカウントのカラムとして**右隣に開く。⚠ 「すべての通知」カラム自体はアカウントをまたぐので、`DeckColumn` のアカウント（コンテナ）をどれにするかは実装時に決める

### 8. デッキは**別画面として足す**。タブ UI はそのまま残す（2026-09-17 pooza 決定・[#1092](https://github.com/pooza/capsicum/issues/1092)）

> Mastodon ライクだし、いままでの操作で慣れている人にも違和感ない（pooza）

- **HomeScreen（タブ UI）には手を入れない。**デッキを使わない利用者に影響が出ない（#1092 の完了条件がそのまま成り立つ）
  - ⚠ **2026-09-22 更新（[#1153](https://github.com/pooza/capsicum/issues/1153)・pooza 決定）: 例外は「切り替えのアイコン 1 点」だけ。**タブ UI の AppBar に「デッキ表示に切り替え」、デッキの AppBar に「タブ表示に切り替え」を**対称に**置く（ドロワーの 1 項目では他の画面遷移と見分けがつかない、という実使用からの要望）。置き場所は AppBar のアイコンにした（狭幅運用で横幅を食うのはアイコン 1 個ぶん）
  - ⚠⚠ **見た目は切り替えスイッチ・実体は画面遷移のまま。**デッキは `push('/deck')`、戻りは `go('/home')`。**`go('/home')` は下に残っている HomeScreen を作り直さない**（go_router が同じページを使い回す）ので、下の前提（HomeScreen が同じ TL を watch し続ける）は崩れない。**「モード」として持つ形にはしない**——現在のアカウントのカラムが HomeScreen と購読を共有する前提が崩れる。`deck_switch_test` で固定（`push('/home')` にすると 2 枚目が積まれて落ちる）
- デッキは**独立したルート**（`/deck`）として開く。**入口はドロワー等に足す**（具体の置き場は #1094 で決める）。ドロワーの「デッキ」項目も残してある
- ⚠ **7-1（常駐ドロワーをデッキ時だけ出さない）は「デッキ画面は常駐ドロワーを持たない」に読み替わる。**HomeScreen の `width >= 900` 判定を触る必要は無くなった
- ⚠⚠ **デッキ画面を push すると、HomeScreen は下に残って本線 TL を watch し続ける。**同じアカウントの同じ TL を別コンテナで持つと購読キーがぶつかる（未決事項 10）ので、**現在のアカウントのカラムはルートのコンテナを使う**（→ HomeScreen と同じインスタンスを共有し、購読も 1 本）。**それ以外のアカウントはアカウントごとのコンテナ**。⚠ これは技術判断で、ルートの「現在のアカウント」が変わったら（デッキを閉じて切り替えてから開き直したら）カラムのコンテナの割り当ても変わる

### 9. カラムから開いた投稿・プロフィール等は**新しいカラムとして開く**（2026-09-17 pooza 決定・[#1096](https://github.com/pooza/capsicum/issues/1096)）

参考実装に揃える。**2026-09-17 にソースを実読して確認**（`action/Action_Conversation.kt` / `actmain/ActMainColumns.kt`）:

| | SubwayTooter | capsicum で採る形 |
| --- | --- | --- |
| 挿入位置 | `nextPosition(column)` ＝ **開いた元のカラムの右隣**（元が不明なら既定位置） | 同じ |
| アカウント | 元のカラムの `accessInfo` をそのまま渡す | **元のカラムのアカウントを引き継ぐ**（→ 未決事項 9 の画面遷移ぶんが、スコープの引き継ぎではなく**カラムのアカウント指定**で解ける） |
| 重複 | `AllowColumnDuplication`（**既定 true**）。false なら既存の同じカラムへスクロール | ⚠⚠ **許さない**（[#1182](https://github.com/pooza/capsicum/issues/1182)・2026-09-28 pooza 決定で改めた。**SubwayTooter の `AllowColumnDuplication = false` と同じ振る舞い**）。⚠ **決定済み事項 6-2 が重複を許すのは「カラム設定から足す」入口だけ**（下の 9-2） |
| 対象 | 会話（`ColumnType.CONVERSATION`）・プロフィール（`ColumnType.PROFILE`）ほか | 投稿（スレッド）・プロフィール・ハッシュタグ・リスト等、**カラムの中身として成り立つもの** |

- ⚠ **カラムの中身の種類が増える。**今の `TabType` は TL 系（本線 / リスト / ハッシュタグ / チャンネル / 通知 / お知らせ）だけで、**投稿スレッドとプロフィールが無い**。永続化の書式（`DeckColumn`・`<id>|<アカウント>|<種別>`）はそのまま使えるが、種別を足す
- **振り分けは 1 箇所に寄せる。**URL タップを `openFediverseLink` に集約した #1030 と同じ形で、「投稿を開く」「プロフィールを開く」を**デッキの中ならカラムを足す・外なら今どおり push** に出し分ける入口を作り、素の `context.push('/post' …)` 等を走査で止める
- ⚠ **カラムにならないものは残る**: 投稿フォーム（返信・引用）/ メディアビューア / BottomSheet / Dialog。これらは**全画面・重ね表示のまま、カラムのスコープを引き継ぐ**必要がある（未決事項 9 の残り）

**実装（2026-09-17・[#1148](https://github.com/pooza/capsicum/issues/1148)）:**

- 種別は `TabType` に `PostThreadTab(postId)` / `ProfileTab(userId)` を足した（**デッキ専用・タブ UI には出ない**）。保存は id だけで、開いた時点の `Post` / `User` は `DeckColumn.seed`（保存しない）で渡す。**読み戻したカラムはカラムのアカウントで `getPostById` / `getUserById` し直す**（id はサーバーローカル）
- 振り分けは `openPost` / `openProfile` / `openHashtag`（`ui/util/deck_navigation.dart`）。カラムの位置に `DeckColumnScope` を置き、**`InheritedTheme` にして長押しシート等の中にも持ち込む**（#1149 の `ProviderScopeCarrier` と同じ仕組み）。素の `push('/post' …)` は `deck_navigation_guard_test` が止める
- 中身は既存の `PostDetailScreen` / `ProfileScreen` を `embedded: true` で描く（**戻るボタンを出さない** —— `pop` はデッキ画面ごと閉じる）。閉じるのはカラムのヘッダーの × ボタン（全カラムに付けた）
- **カラムの中身から開く一覧・画面もカラムにした**（2026-09-17 pooza 決定・[#1150](https://github.com/pooza/capsicum/issues/1150) 案 A）: ユーザー一覧（フォロー / フォロワー / お気に入り / ブースト / 絵文字ごとのリアクション）・引用一覧・実績・コレクション一覧・コレクション・ギャラリー投稿・Play・メッセージ（相手ユーザー）・チャンネル。種別は `TabType` の中間クラス `DeckOnlyTab` の下に置き、**タブ UI 側の `switch` は `DeckOnlyTab()` の 1 ケースで受ける**。見出し・取得関数は `ui/util/deck_tabs.dart` にまとめ、**全画面の push とカラムで同じものを使う**（`/users` の fetcher を組むのもここ）
- ⚠ `/users` / `/posts` は「タイトルと fetcher（クロージャ）」を渡す汎用画面なので**そのままでは保存できない**。種類と対象 id（`users:<種類>:<id>[:<絵文字>]`）に分解して保存し、描くときにカラムのアカウントのアダプタで fetcher を組み直す
- ⚠ **編集フォーム（`/profile/edit`）はカラムにしない**。投稿フォームと同じく `extraWithProviderScope` でスコープを運ぶ（運ばないと、別アカウントのカラムにある自分のプロフィールから現在のアカウントを編集する）
- 中身の画面が自分を閉じる（コレクションを削除した等）ときは `screenCloser(context)` を使う。カラムの中ではカラムを外し、外では pop する（**pop するとデッキ画面ごと閉じる**）
- 対象外: 新規メッセージ画面の `pushReplacement`（画面自体がカラムにならない）と通知タップ（`main.dart`・カラムの外）

#### 9-2. ⚠⚠ 操作から開いたカラムは重複させない（2026-09-28 pooza 決定・[#1182](https://github.com/pooza/capsicum/issues/1182)）

**当初は 6-2 に揃えて「重複を許す」としていたが、改めた。**6-2 で重複を許した根拠は「同じ TL を 2 本並べたい」という使い方（カラム設定から意図して足すもの）で、**操作の結果として開くカラムには当てはまらない**。同じ中身が 2 本並んでも得るものは無く、ユーザーの意図に反して増えるだけ。

⚠⚠ **区分は種別ではなく入口。**コード上もこの 2 つは入口が分かれている:

| 入口 | 通り道 | 重複 |
| --- | --- | --- |
| カラム設定から足す | `DeckColumnsNotifier.add`（`deck_columns_sheet.dart` のみ） | **許す**（6-2 のまま） |
| 操作の結果として開く | `DeckColumnsNotifier.insertAfter`（`deck_screen.dart` の `_openColumn` に集約） | ⚠ **許さない**（⚠⚠ **例外は検索カラムだけ** → 9-2-1） |

- **同じものの判定は `(AccountKey, TabType)`** ＝ 既存の `DeckColumn.contentKey`（`<アカウント>|<種別>`・4-3）。⚠ **アカウントをキーから落とさない** —— 投稿・プロフィールの ID はサーバーローカルなので、落とすと**別アカウントのカラムから開いたときに別のものを指す**
- 既に同じカラムがあれば**新しく作らず、そのカラムへスクロールして点滅させる**（押したのに何も起きないと見えるのを防ぐ）
- ⚠ **既存カラムの位置は動かさない**（開いた元の右隣へ移さない）。スクロールで見せるだけ
- ⚠ **判定は `insertAfter` の中に置いた**（`_openColumn` ではなく）。入口さえ通れば呼ぶ側に関わらず成り立つ。⚠ **直接 `insertAfter` を呼ぶ入口を増やさない**
- **「すべての通知」の個別判定（#1173）はこれに吸収された。**アカウントがキーに入っているので、単一アカウントの通知がアカウントごとに別カラムになる性質もそのまま成り立つ

#### 9-2-1. 検索カラムだけは重複できる（2026-10-03 pooza 決定・[#1193](https://github.com/pooza/capsicum/issues/1193) 案 B）

⚠⚠ **9-2 の根拠が検索には当たらない。**9-2 が重複を禁じた理由は「同じ中身が 2 本並んでも得るものは無い」で、対象は**開いた投稿・プロフィールへのナビゲーション**だった。AppBar の検索ボタンは「この中身を見せて」ではなく **「検索の道具を 1 本ください」**という操作で、⚠ **語が違えば中身も違う**。

**何が壊れていたか**: `SearchTab` は荷物を持たないので `toIdentityKey()` が `search` の 1 語になり、`contentKey` が `<アカウント>|search` になる。したがって**同じアカウントの検索カラムは全部同一視され**、2 本目を開くと 1 本目へスクロールして戻っていた。⚠ **「別のアカウントで 2 本」は壊れていない**（アカウントがキーに入っている）。

- **直し方は `insertAfter` の判定で `SearchTab` を対象外にするだけ**（`preferences_provider.dart`）。⚠⚠ **種別で例外を作るのはここ 1 箇所だけ**で、増やすならこの節を先に直す
- ⚠ **保存形式は動かさない。**`SearchTab` に検索語を持たせて `contentKey` を割る案（#1193 案 A）は**採らない** —— 保存形式 `<id>|<アカウント>|<種別>` に語が載るので (a) 語に `|` が入ると `deserialize` が割る位置を間違える（エスケープが要る・#1159 の `HashtagTab` と同じ型）、(b) ⚠⚠ **何を検索したかが端末に残る**（いまは残らない）
- **引き換えに、検索ボタンを 2 回押すと空の検索カラムが 2 本並ぶ。**⚠ 語が入る前は見分けが付かない。**これは受け入れた** —— 押した回数ぶん道具が増えるのは筋が通っており、空のカラム同士を弾くには語を列側へ持ち上げる配線（上の (a)(b) を呼ぶ）が必要になる
- ⚠ **実行時の状態はもともと独立している。**`SearchScreen(embedded: true)` は語・結果・タブ・エラーを自分の `State` に持つので、2 本並べても混ざらない。`contentKey` が共有するのはタイムライン系の provider（6-2 / B-1）で、**検索はそこに乗っていない**
- **シートの候補に「検索」を足す案（#1193 案 C）は [#1216](https://github.com/pooza/capsicum/issues/1216) へ分けた。**入口を増やす話で、本題が直れば困らない → **9-2-2 で済んだ**

#### 9-2-2. 候補に出すのは「荷物を持たない `DeckOnlyTab`」（2026-10-04 pooza 承認・[#1216](https://github.com/pooza/capsicum/issues/1216)）

⚠⚠ **「検索だけ例外で足す」ではなく構造で線を引いた。**`docs/CLAUDE.md`「判定を書くときの原則」の **列挙をやめ、構造で見る**をそのまま当てた —— 名前の表にすると、**次に増えた種別が黙って候補から漏れる**。

| 性質 | 候補 | 理由 |
| --- | --- | --- |
| **荷物を持たない**（引数なしで構築できる） | ✅ 出す | **それ自体で成立する道具。**何を開くかが決まっている |
| 荷物を持つ（対象の ID が要る） | ❌ 出さない | ⚠ **シートから「足す」ことに意味がない** —— 何を開くか決まっていない |

**2026-10-04 時点で前者は 2 つだけ**（`SearchTab` / `AllNotificationsTab`）。後者は `PostThreadTab` / `ProfileTab` / `UserListTab` / `QuotesTab` / `AchievementsTab` / `CollectionsTab` / `CollectionTab` / `GalleryPostTab` / `FlashTab` / `ChatUserTab` の 10。

- ⚠ **`AllNotificationsTab` には追加の条件がある**（アカウントが 2 つ以上・決定済み事項 7-3）。**1 つなら上の「通知」と中身が同じ**になるため。⚠ **この条件は構造では出てこない**ので、例外として残す
- ⚠⚠ **検査で固定した**（`test/deck_sheet_candidates_guard_test.dart`）。`tab_type.dart` から「引数なしの `DeckOnlyTab`」を走査し、**全部が `_localCandidates` に実在する**ことを見る。**荷物を持たない種別を足したら落ちる**ので、そのときにこの節へ判断を書き足す
- **重複はここでも 6-2 のまま許す。**⚠ 9-2-1 が `insertAfter` 側で検索を例外にしたのと**揃う** —— どちらの入口からも検索カラムは 2 本目を置ける

### 10. 新規投稿は**カラムのアカウント**で開く。デッキに**フォーカス中のカラム**を持たせる（2026-09-26 pooza 決定・[#1172](https://github.com/pooza/capsicum/issues/1172)）

⚠ **設計の当初の論点から漏れていた**（実使用からの指摘・2026-09-22）。論点にあったのは「開いたフォームにカラムのアカウントを引き継ぐ」だけで、**新規投稿の入口をどこに置くか**が無かった。デッキは複数アカウントのカラムが並ぶので、タブ UI（常に現在のアカウント）の前提が使えない。

**入口は 3 つ。どれも「どのアカウントで投稿するか」を画面上で見せる:**

| 入口 | アカウント |
| --- | --- |
| カラムの見出しの投稿ボタン（案 A） | **そのカラム**のアカウント。見出し（#1152 のアイコン・表示名・サーバーの色）で誰として投稿するかが見える |
| メニューバーの「新規投稿」（⌘N / Ctrl+N） | **フォーカス中のカラム**のアカウント（詳細は [#1170](https://github.com/pooza/capsicum/issues/1170)） |
| 画面下端の簡易投稿バー（デッキ全体で 1 本） | **フォーカス中のカラム**のアカウント。バーの左端にそのアカウントのアイコンを出す。⚠ カラムごとに置く案は採らない（カラム数ぶん縦を食う・375px では入力欄が短すぎる） |

- ⚠ **B 案（画面に 1 つ置き、開くたびにアカウントを選ぶ・SubwayTooter の形）は採らない。**毎回選ぶ手間と、選び間違いによる誤投稿のため
- **投稿フォームはカラムにならない**（決定済み事項 9 のとおり全画面・`extraWithProviderScope`）。したがって**フォームの幅はウィンドウ幅**で、狭さはタブ UI と同条件。狭幅での使い勝手は [#1167](https://github.com/pooza/capsicum/issues/1167)（投稿画面の下のアイコン列）が両方に効く

**カラムの種類ごとの初期状態**（見出しのボタン・簡易投稿バーとも）:

| カラム | 開いたときの状態 |
| --- | --- |
| ハッシュタグ | 本文の末尾に `#タグ`（AND 指定なら全部・⚠ spec は `hashtagSpecTags` で分解してから・#1159）。カーソルは本文の先頭 |
| チャンネル（Misskey） | **そのチャンネルへの投稿**（`channelId`）。⚠ 無いとチャンネルの外へ出るので必須 |
| その他 | 空 |

⚠ **タブ UI のハッシュタグ画面も揃える。**簡易投稿バーから送るとタグが付くのに、**バーから投稿フォームを開くとタグが引き継がれていなかった**（2026-09-26 に発見・#1172 の範囲に含める）。

**フォーカス中のカラム**（⌘N・簡易投稿バー・[#1157](https://github.com/pooza/capsicum/issues/1157) / #1170 の「カラムの更新」の宛先）:

- **見せ方**: フォーカス中のカラム全体を**アクセント色の枠**（2px 程度・テーマの色 1 色）で囲む。⚠ 見出しの濃淡や印では表さない（見出しの色はサーバーごとにばらばらで、組み合わせ次第で見分けが付かなくなる）。**同時に見えているカラムが 1 本のときは枠を出さない**（[#1243](https://github.com/pooza/capsicum/issues/1243)・2026-10-06 pooza。⚠ 当初は「列に 1 本しかないとき」だったが、狭幅では見えているカラムがフォーカスなのが自明で、枠がうるさいという声が出た。幅広の環境ではフォーカスを知る手がかりが要るので残す）
- **移る契機**: カラムの中の**クリック / タップ**（どこを押しても）。⚠⚠ **スクロールだけでは移さない**（ホイールで読むだけのことが多く、読んでいたカラムのアカウントで ⌘N が開いてしまう）
- 狭幅で 1 本ずつしか見えないときは、**見えているカラムがフォーカス**（横に送ると移る）
- #1170 の「表示 > カラム」で選んだカラムは、そこまで送ってフォーカスも移す
- ⚠ **カラムから開いたカラム**（スレッド・プロフィール・検索・通知から開いた投稿など・決定済み事項 9）は**開いた時点でフォーカスになり、足した直後に枠を 1 回点滅させる**（0.5 秒程度・⚠ **常時の枠を出さない幅でも点滅は出す** —— いま見えているカラムを開き直す操作は、点滅が無いと何も起きないように見える）。横送りで列がずれても、どこに出たかを見失わないため（2026-09-26 pooza）。アカウントは元のカラムを引き継ぐので、⌘N の宛先のアカウントは変わらない
- 初期値は先頭のカラム。フォーカス中のカラムを閉じたら隣へ移る
- カラム間を移るキーボードショートカットは入れない（要るなら #1170 で）

### 11. メニューバーはタブ UI 前提の 3 か所だけ差し替える（2026-09-26 pooza 決定・[#1170](https://github.com/pooza/capsicum/issues/1170)）

⚠ **メニューバーを丸ごと隠す案は採らない**（macOS の「終了」や編集メニューまで消える・2026-09-22 合意）。「デッキ中か」は `mountedDeckCountProvider`（#1099）で判定する。

### 12. 背景画像はデッキでは出さない（2026-09-26 pooza 決定・[#1174](https://github.com/pooza/capsicum/issues/1174)）
