## 決定済み事項

### 1. 現状の棚卸し（実測）

#### 1-1. relay の認証は共有シークレット 1 本。認可は無い

```ruby
# capsicum-relay/lib/relay/base_app.rb:120
def authenticate!
  secret = settings.config['shared_secret']
  provided = request.env['HTTP_X_RELAY_SECRET']
  return if provided == secret
  ...halt 401
end
```

- **全エンドポイントがこれだけ**（`/register` / `/push` / `/supporters` / `/announcement_subscriptions`）
- ⚠⚠ **このシークレットは全クライアントに配られている。**`--dart-define=RELAY_SECRET` でビルド時に**バイナリへ埋め込まれる**（[dev-environment.md](dev-environment.md)）。**取り出せる**
- → **現状は「capsicum を持っている人は誰でも relay を使える」。**無償サービスなので実害が小さいだけで、**課金を始めた瞬間に、迂回する経済的動機が生まれる**

⚠ **共有シークレットを廃止する必要は無い**（API 面の粗いフィルタとしては働く）。**認可の境界として使うのをやめる**、が正しい。

#### 1-2. プリセット判定はクライアント側にしかない。しかも意図的な穴がある

```dart

```

⚠⚠ **つまり「プリセットに 1 アカウント持てば、外部サーバーのアカウントも全部無償でリレーされる」。**これはバグではなく doc コメントに明記された仕様（「プリセットサーバーのアカウントを1つでも持っていれば、全アカウントを登録対象とする」）。

→ ⚠⚠ **有償化したとき、この穴が有償商品を素通りさせる。**⚠ **これが本件で最も重い設計上の論点**（未決事項 3）。

⚠⚠ **穴は実際に通られている。ただし通っているのは「外部ユーザー」ではない**（2026-09-06 実測・本番 DB の `subscriptions`）。

#### 1-5. ⚠ スケールの階段 — 先に効くのは同時実行数、その次にプラン

**2026-09-06 に flauros 上で実測した**（`journalctl` 7 日分 4,108 件の `latency_ms` と本番 DB）。

⚠⚠ **初稿の「詰まるのは RAM ではない」は論点のすり替えだった**（2026-09-06 pooza の訂正）。**VPS はメモリ容量でプラン全体（CPU コア数・帯域）が決まる慣習**なので、「1GB では耐えられなくなる」は**プランを上げることになる**という意味であって、RAM 単体の話ではない。⚠ **「1GB」はプラン名であって症状名ではない。**下の階段は「プランを上げる前にやれることがある」という話で、**プランを上げる日が来ないという主張ではない**。

| 指標 | 実測 |
| --- | --- |
| ホスト | flauros = **1 vCPU / RAM 961MB / disk 25GB**（uptime 128 日・load average **0.00**） |
| relay プロセス | RSS **約 65MB**。DB は SQLite で **335KB**（WAL 4MB） |
| ⚠ **同時実行数** | ⚠⚠ **puma は `workers 0` / `threads 2`。同時に 2 通しか捌けない** |
| 配送レイテンシ | **p50 168ms / p90 3,227ms / p99 4,581ms / max 8,976ms** |
| ピーク流入 | **21 通/分**（7 日間の最大・0.35 通/秒） |

⚠⚠ **p90 が p50 の 19 倍なのは Windows（WNS）**。実測ログで iOS が 173〜174ms のところ、WNS は **3,722ms** かかっている。**遅い 1 通が 2 本しかないスレッドの片方を 3.7 秒間占有する。**

**容量の見積もり**（現在の device_type 構成 = windows 18% で加重平均すると 1 通あたり約 0.77 秒）:

- 理論容量 ≒ **2 スレッド ÷ 0.77 秒 = 約 156 通/分**
- 実測ピーク **21 通/分 = 容量の約 13%**
- → ⚠ **飽和は現在の 7〜8 倍。サブスク 158 件に対して 1,200 件前後が目安**

⚠⚠ **ただし Windows 比率が上がると容量が急落する。**仮に全員 Windows なら 2 ÷ 3.5 秒 = **34 通/分**しか出ず、**現在のピーク 21 通/分に対して 1.6 倍の余裕しかない**。⚠ **「利用者が何人か」より「どの OS か」で先に詰まる。**

**次の段は「お金」ではなく「実装」**（順に安い）:

| 順 | 打ち手 | 費用 | 効き |
| --- | --- | --- | --- |
| 1 | **`threads` を 2 から上げる** | **0 円** | ⚠ **配送は外部 API の I/O 待ちが支配的**なので、1 vCPU でもほぼ線形に伸びる。**今の設定が保守的すぎる** |
| 2 | **配送を非同期化**（受信して即 202、送信はワーカー） | 実装のみ | 遅い WNS が受信経路を塞がなくなる |
| 3 | **`workers` を増やす** | 0 円 | ⚠ **1 vCPU なので効果は限定的**。メモリには余裕がある（65MB × N） |
| 4 | **プランを上げる** | ⚠ **ここで初めて費用が増える** | コア数・帯域が上がる（⚠ **メモリ容量でプランが決まるので、実質「1GB → 2GB → 4GB」という刻み**） |

⚠ **したがって「人数が増えたら VPS 代が上がる」は、1〜3 を使い切った後の話。**⚠ **逆に 1〜3 を放置したまま増員すると、プランを上げても直らない**（load average 0.00 のホストで「重い」が起きている状態は、コアを足しても `threads 2` のままなら変わらない）。

⚠ **「重い」の実体は CPU 仕事ではなく待ち時間。**p90 の 3.2 秒はほぼ全部が **WNS の応答待ち**で、relay 自身は暇（load average 0.00）。⚠ **待ちは並行数で吸収するものなので、まず 1〜2 が効く。**ただし Ruby の GVL があるため**復号など CPU を使う部分は並行しない** — ⚠ **1 を入れた後にもう一度実測して、どこで頭打ちになるかを見ること**（机上で断定しない）。

### 2. 必要なものは 3 層。「ゲート 1 個」ではない

| 層 | 問い | 現状 | 要るもの |
| --- | --- | --- | --- |
| **A. 認証** | この要求は誰から来たか | ⚠ **無い**（`account` / `server` は自己申告の文字列） | relay が発行する端末ごとの token |
| **B. 課金の検証** | 本当に払ったか | ⚠ **無い** | ストアのサーバー API でレシート検証 + 失効の追随 |
| **C. 認可** | 通してよいか | ⚠ **無い**（共有シークレットのみ） | `/register` と **`/push`** の両方でゲート |

⚠ **A → B → C の順に依存する。**C だけ足しても、A が無ければ「誰の entitlement か」が言えない。

#### 2-A. 認証 — **課金は fedi アカウントではなくストアアカウントに紐づく**

⚠⚠ **ここは設計の分岐点で、素直な答えがある。**

購入は **Apple ID / Google アカウント / Microsoft アカウント**に属する。fedi アカウントには属さない。したがって:

- **entitlement の主体は「購入」であって「fedi アカウント」ではない**
- **1 つの購入に複数の fedi アカウントをぶら下げる**のが自然（capsicum は元々マルチアカウント）
- fedi アカウントの所有証明（relay が Mastodon へ問い合わせる等）は **要らない**。⚠ **relay にユーザーのアクセストークンを持たせない**という現行の設計を崩さずに済む

→ **relay が購入に対して opaque な `entitlement_token` を発行し、クライアントが保持する。**`/register` はそれを提示する。

#### 2-B. 課金の検証 — ⚠ **3 ストア分の実装が要る**

| ストア | 要るもの |
| --- | --- |
| Apple | App Store Server API（+ App Store Connect API キーを relay に置く）/ App Store Server Notifications V2 の受け口 |
| Google | Play Developer API（+ サービスアカウント）/ Real-time developer notifications（Pub/Sub） |
| Microsoft | Store collection / purchase API（Windows IAP は [#599](https://github.com/pooza/capsicum/issues/599)・v1.43 で出荷済み） |

⚠⚠ **サブスクは「1 回検証して終わり」ではない。**更新・失効・返金・支払い猶予（grace period）・課金リトライの状態を追い続ける必要がある。**両 Issue が触れていない最大の工数がここ。**

⚠ **通知の受け口は relay の新しい公開エンドポイントになる。**署名検証が要り、**capsicum クライアントとは無関係の面が増える**（運用対象が増える）。

#### 2-C. 認可 — ⚠ **ゲートは `/register` だけでは足りない**

**Web Push の購読は fedi サーバー側が保持している。**relay で登録を拒んでも、**既存の購読は生き続けて `/push/{push_token}` を叩き続ける**。

→ **失効時に止めるのは `/push`。**しかも ⚠ **`410 Gone` を返すのが正しい** — Mastodon / Misskey は Web Push の 410 で購読を掃除するので、**サーバー側にゴミを残さず、無駄な配送も止まる**。⚠ **黙って捨てる（200 を返す）と、失効後も fedi サーバーが永久に叩き続ける。**

⚠⚠ **プリセットは絶対に巻き込まない。**ゲートは **「非プリセット かつ entitlement 無し」のときだけ**閉じる。⚠ **fail-open にする**（判定不能・ストア API 不達のときは通す）。**課金の判定が落ちて無償ユーザーの通知が止まるのは、取り返しがつかない**。

| **1GB（現行）** | ¥750 | 〜400 人 | **4 人** | ⚠ **1%** |
| 2GB | ¥1,800 | さらに上 | 9 人 | 2%台 |
| 4GB | ¥3,600 | さらに上 | 18 人 | 数% |

⚠⚠ **「4 人ぶんの収入で 400 人が乗る箱」という構造。**プランを上げる日が来るのは**利用者が増えたとき＝有償者の母数も増えているとき**なので、**階段を越える原資は同時に増える**。⚠ **これは「限界費用がほぼ 0」の正しい使いどころ** — 有償化を否定する材料ではなく、**少人数から黒字にできる**という材料だった。

⚠ **前提: 1-5 のチューニング（`threads`）を先にやること。**`threads 2` のままだと 400 人まで伸びず、上の表の分母が崩れる。⚠ **つまりチューニングは「性能改善」ではなく「損益分岐の前提条件」。**

#### ⚠ 残る問題: 既存 57 サブスクは無償のまま

⚠⚠ **上の試算は「外部 25 人のうち何人かが払う」を前提にしているが、その 25 人は今すでに無償で使えている。**非目標「既存の無料プッシュを課金化ではない」を守るなら、**この人たちからは 1 円も入らない**（未決事項 3 の a / b）。

→ ⚠ **「持ち出しゼロ」の分母を、既存 25 人に求めるのか、これから来る新規に求めるのかで、必要な時間がまるで違う。**⚠ **未決事項 3 は設計の論点ではなく、収益目標が達成できるかどうかの論点になった。**

## 未決事項

### 1. ⚠⚠ 事業判断（これが最大の未決・pooza が決める）

[roadmap.md](roadmap.md)「未決事項 2」のとおり技術ブロッカーは無い。⚠ **ただし本設計書で工数の実像が変わった**ので、判断材料として置く。

- **作るもの**: 認証層 + 3 ストア分のレシート検証 + サブスク状態の追随 + 認可ゲート + サブスク SKU の審査

#### ⚠⚠ 2026-09-06 訂正: 「限界費用が 0 だから動機が弱い」は誤り

**初稿は「限界費用はほぼ 0 なので、運用コストの補填という建付けは実費ベースでは動機として弱い」と書いていた。これは間違い**（2026-09-06 pooza の指摘: 「**お金はけっこうかかってます**」）。

⚠ **誤りの構造: 増分費用だけを見て、固定費と投下工数を勘定から落としていた。**

| | 実態 |
| --- | --- |
| **限界費用**（ユーザーが 1 人増えたときの追加費用） | **ほぼ 0** で正しい。push 送信は APNs / FCM / WNS とも従量課金が無く、payload は 4〜5KB 上限 |
| **固定費** | ⚠ **かかっている。**relay は flauros（Linode）という箱を必要とし、**利用者が 0 人でも毎月出ていく**。加えて配布を続けるための年額（Apple Developer Program 等）・ドメイン・認証鍵の管理 |
| **投下工数** | ⚠ **最大の投下資源。**3 ストア分のレシート検証・失効の追随・認可ゲートは、**無償のままなら絶対に作らない量** |

**限界費用が 0 に近いことの正しい含意は「有償化の動機が無い」ではない。**

- ✅ **価格を従量にする必要が無い** — 1 人あたりの原価を積み上げて値付けする構造ではない
- ✅ **固定費回収型（サブスク）が構造に合う** — 未決事項 5 でサブスク一択としたのと整合する
- ✅ **利用者が増えても赤字が膨らまない** — 上限リスクが小さいので、**少人数から始められる**

⚠ **したがって判断軸は「1 人あたりいくら儲かるか」ではない。**「**固定費と工数を賄える最小人数に届くか**」。ここが本当の未決。

#### ⚠⚠ さらに: 「回収」を目標に置くと、この企画は必ず失敗する

**2026-09-06 pooza の 3 点**:

1. **人数が増えたら 1GB VPS では耐えられなくなる** → ⚠ **1-5 で実測した。**正しいが、**先に詰まるのは RAM ではなく `threads 2`**。次の段は 0 円の設定変更から始まる
2. **インフラ費用も開発費も、普通なら趣味にはかけない金額**
3. ⚠⚠ **受託開発案件だとしたら、到底回収できない**

**3 が結論を決めている。**開発工数を人件費で評価した瞬間に、想定しうるどんな価格 × どんな人数でも回収に届かない。⚠ **つまり「開発費の回収」を KPI に置く限り、この企画は永久に「やらない」が正解になる。**

→ ⚠⚠ **回収**以外の理由が要る、というのが pooza の到達点。以下は**材料**（⚠ **どれを採るかは製品判断。本書は推奨を付けない** — 初稿でその線を踏み越えた）。

| | 理由の候補 | 実測との対応 |
| --- | --- | --- |
| ~~a~~ | ~~**需要は既に存在する**~~ | ⚠⚠ **撤回。**初稿は「外部サーバーが 36%」を需要の証拠としたが、**人で数えるとプリセット非保有は 0 人**だった（1-2）。**需要は未証明** |
| ~~b~~ | ~~**「既に届けているものへの対価」**~~ | ⚠⚠ **撤回。**届けている相手は全員プリセットのメンバー |
| c | **責任範囲を対価で画定する** | 現状は「外部サーバーはサポート優先度を下げる」方針（[CLAUDE.md](CLAUDE.md)）なのに**プッシュだけ無償で完全に提供している**というねじれがある |
| d | **回収の分母を「relay の固定費」に絞る** | ⚠ **開発費を諦めてインフラ実費だけに目標を置けば桁が変わる。**1-5 のとおり relay は 1 ホストに収まっている |

⚠ **d は「安く見せる」ための切り分けではない。**開発費は**すでに沈んだ費用**（[#597](https://github.com/pooza/capsicum/issues/597) をやらなくても戻ってこない）なので、**これから先の意思決定にだけ効く費用＝インフラの増分**で判断する、という筋の話。

- ⚠ **実額は pooza が持っている。**上の表に数字を入れるのは本書の宿題（未記入）
- ⚠ **ストア手数料 15〜30% と、サブスクの継続的な運用負荷**（失効処理・問い合わせ・返金）が乗る。**課金しないほうが運用は安い**ので、そのぶんを超える回収が要る

⚠ **判断を先回りしない。**[roadmap.md](roadmap.md) は #597 を「収益の柱・逃がさない」と決めており、**本書はそれを覆す提案をしない**。⚠ **初稿は「動機として弱い」と書いた時点で、事実上それを覆しにかかっていた。**同じ形（技術的な整理から製品判断を再導出する）を繰り返さない。上は判断の材料。

### 2. 認証の具体（フェーズ 1 の設計）

- `entitlement_token` の発行単位は「購入」か「端末」か。⚠ **購入は複数端末で復元される**（サブスクはストアの購入復元対象）ので、**端末ごとに発行して購入へ束ねる**形が素直に見えるが未確定
- 既存の登録（`subscriptions` テーブル）との関係。⚠ **移行時に既存ユーザーの通知を止めない**こと
- ⚠ **共有シークレットは残す**（1-1）。二重にする

### 3. ⚠⚠ 「プリセット 1 アカウントで全部無償」の穴をどうするか

**本件で最も答えにくい論点。**

- 現状（1-2）: プリセットに 1 アカウント持てば、**外部アカウントも全部無償でリレーされる**
- 有償化すると: **プリセットサーバーにアカウントを 1 つ作るだけで有償商品を迂回できる**
- ⚠ しかし塞ぐと: **既にその状態で使っている人の通知を止める**ことになり、[#597 本文](https://github.com/pooza/capsicum/issues/597)の「**(B) 既存の無料プッシュを課金化 ではない**」という明示的な非目標に抵触する

選択肢（⚠ **どれも一長一短で、製品判断**）:

| | 案 | 含意 |
| --- | --- | --- |
| a | **穴を残す** | 迂回は容易。⚠ **ただし迂回にはプリセットサーバーへの登録が要る**ので、pooza が入口を握っている。実害は「うちのサーバーに人が増える」だけ、とも読める |
| b | **新規のみ塞ぐ**（既存の登録は grandfather） | 非目標に抵触しない。⚠ **実装が複雑**（いつの登録かを持つ必要がある） |
| c | **穴を塞ぐ** | 有償商品として筋は通るが、⚠ **既存ユーザーの通知が止まる**。非目標に正面から抵触 |

⚠ **a の再評価が要る。**「迂回できる」を欠陥と見るか、「プリセットサーバーへの導線」と見るかで結論が変わる。**capsicum の主目的は自前インフラとの連携**（[CLAUDE.md](CLAUDE.md)）なので、**外部ユーザーがプリセットに来ること自体は目的と矛盾しない**。

### 4. サブスクの失効をクライアントへどう伝えるか

- 失効したとき、ユーザーには**何がどう見えるか**。⚠ **「いつのまにか通知が来ない」が最悪**
- `/push` が `410` を返すと fedi サーバー側の購読が消えるので、**復帰時は再登録が要る**。その導線
- ⚠ **設定→プッシュ通知の登録ステータス画面**（`feedback_push_debug_check_status_screen_first` の画面）に状態を出すのが自然。既にある器を使う

### 5. 価格

⚠ **決めるのは事業判断（未決事項 1）の後**。参考: 投げ銭は ¥100 / ¥500 / ¥800 の 3 階層（[supporter-subscription-plan.md](supporter-subscription-plan.md) B-2）。

#### ⚠ 設定できる下限は「投げ銭と同じ」ではない

**Apple は 2026-09-06 に ASC API で実測した**（`GET /v2/inAppPurchases/{id}/pricePoints?filter[territory]=JPN`・既存の `supporter.tip.small` を基点）:

| | 実測 / 目安 | 出典 |
| --- | --- | --- |
| **App Store** | ⚠⚠ **最低 ¥50。しかも 10 円刻み**（¥50 / 60 / 70 / 80 / 90 / 100 / 110 …） | **実測**（200 件取得・最小値 50.0） |
| Google Play | 日本の最低はおおむね **¥100** 前後 | ⚠ **未実測。**Play Console で要確認（設定可能な下限は API に出ない） |
| Microsoft Store | 価格帯（tier）制で **$0.99 相当**が下限 | ⚠ **未実測。**Partner Center で要確認 |

⚠⚠ **[supporter-subscription-plan.md](supporter-subscription-plan.md) B-2 の「App Store の価格ポイントが ¥1,000 まで 100 円刻みのため ¥150 → ¥100 に変更」（2026-05-22）は実態と違った。**実際は **10 円刻みで ¥50 から**選べる。⚠ **投げ銭の階層を「下限だから」と説明しないこと。**

⚠ **ただしサブスク用の価格ポイントは別リソース**（`/v1/subscriptions/{id}/pricePoints`）で、**サブスク商品を 1 つ作らないと API で引けない**。上の ¥50 は**消耗型で確認した値**。⚠ **サブスクでも同じ下限かは未確認**（Apple は 2023 年の価格体系刷新で全 IAP 種別の価格ポイントを共通化しているので同じ見込みだが、**確認するまで確定として扱わない**）。

#### ⚠ 安くするほど必要人数が増える

**§6 の損益分岐（flauros 仮 ¥750/月）と突き合わせると**:

| 月額 | 手取り（30%→15%） | 必要人数 |
| --- | --- | --- |
| ¥50 | ¥35 → ¥42 | ⚠ **18〜21 人** |
| ¥100 | ¥70 → ¥85 | 9〜11 人 |
| **¥300** | ¥210 → ¥255 | **3〜4 人** |
| ¥500 | ¥350 → ¥425 | 2 人 |

⚠⚠ **対象者は現時点で 0 人**（1-2）なので、**「安くして間口を広げる」より「必要人数を減らす」ほうが到達しやすい**構造になっている。⚠ **ただしこれは判断材料であって推奨ではない。**間口を広げる価値の評価は製品判断。

### 6. Linux の扱い

⚠ **Linux にはネイティブ push の経路が無い**（[CLAUDE.md](CLAUDE.md)・[#475](https://github.com/pooza/capsicum/issues/475)）。**Linux ユーザーには売る商品が無い。**AppImage 直配なのでストア課金の経路も無い。⚠ **「買えないプラットフォームがある」ことを商品説明に書く必要がある。**
